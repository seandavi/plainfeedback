## 2. Feature by feature: what it does that we don't

**Question syntax.** Questions are R function calls inside code chunks, not markdown. Types: `text`, `textarea`, `numeric`, `mc`, `mc_multiple`, `mc_buttons`, `mc_multiple_buttons`, `mc_image`, `mc_multiple_image`, `select`, `slider`, `slider_numeric` (incl. range), `date`, `daterange`, `matrix`, `matrix_multiple`, plus custom HTML-widget types ([question-types](https://surveydown.org/docs/question-types), NEWS 1.3.0). Options are `c("Label" = "value")` (display text separate from stored value). We have 5 types; we lack dropdown, slider, date, image choice, and a separate stored value for options. Our `.likert` (one shared scale, per-statement ratings) is more survey-native than their `matrix`. The syntax is worse for non-programmers (R vectors, quoting, commas) than our fenced divs; the project itself ships a GUI (`sdstudio`) to compensate.

**Required.** Not a per-question attribute. It is a list in the YAML header (`required: [q1, q2]` or `all-required: true`); unanswered ones block Next on that page and highlight red ([survey-settings](https://surveydown.org/docs/survey-settings)). Our inline `required` flag is better (co-located with the question).

**Skip logic / conditionals.** Defined in `app.R`'s `server()`, separate from the question, as R formulas `<condition> ~ "target_id"`:
- `sd_show_if(sd_value("penguins") == "other" ~ "penguins_other")` shows a question *or page*; `&` combines; `sd_is_answered("id")` is available.
- `sd_skip_if(sd_value("vehicle_ownership") == "no" ~ "screenout")` jumps forward to a later page; skip-back added in v0.15.0 per the roadmap.
- `sd_stop_if(nchar(input$zip) != 5 ~ "Zip code must be 5 digits")` is a validation block that holds the respondent on a page with a message and takes priority over required checks (R source `sd_stop_if` docs in `R/server.R`; NEWS 1.3.0).
Sources: [conditional-logic](https://surveydown.org/docs/conditional-logic), [features-roadmap](https://surveydown.org/docs/features-roadmap). Conditions are arbitrary R evaluated server-side, so there is no safe-expression subset; the author must be trusted. We have nothing yet (phase 3), and our design (safe grammar, shared evaluator) is stricter than theirs by intent.

**Multi-page.** Pages are first-class: `--- page1` shorthand or `::: {.sd_page id=page1}` fence (identical result); automatic Next button; global `show-previous`; per-page `sd_nav(page_next=, label_next=, show_prev=...)`; progress bar (updates per question, not per page); randomization of pages/questions ([page-navigation](https://surveydown.org/docs/page-navigation), [survey-settings](https://surveydown.org/docs/survey-settings), [randomization](https://surveydown.org/docs/randomization) listed, not read). Responses persist when the respondent clicks Next, so partial responses exist; we planned submit-once.

**Reactivity.** Shiny-based: `sd_reactive("product", sd_value("a") * sd_value("b"))`, `sd_output("name", type = "value")` to echo answers into text, reactive questions whose label/options depend on earlier answers (`observe()` + `sd_question()`), piped text, completion codes via `sd_completion_code()` ([reactivity](https://surveydown.org/docs/reactivity)). We have no piping or computed values; none are in our requirements. Cost of the model: every respondent holds a live websocket session on an R process ([performance](https://surveydown.org/docs/performance) page exists; not read).

**Data handling and privacy.** This is where it diverges from us:
- Cookies **on by default** (`use-cookies: yes`): answers and session id are mirrored in the browser cookie to restore a session after refresh ([storing-data](https://surveydown.org/docs/storing-data), [survey-settings](https://surveydown.org/docs/survey-settings)). Can be disabled.
- `capture-metadata` defaults to **TRUE**: the server records user agent (browser/OS), **client IP** (checks proxy headers), and screen resolution into the response row (`R/server.R` around line 603; setting documented in the `sd_server` roxygen). Timestamps per question and page are also stored. The docs pages I read do not mention these fields or anonymity at all.
- Security page: SQL injection prevention, credentials in `.env`, page content served from the server (no HTML source leak), explicitly no SOC2/HIPAA certification; defers hosting/storage compliance to the operator ([security](https://surveydown.org/docs/security)).
- Export: no export feature documented in the pages read; data is viewed in Supabase or via the password-protected `sd_dashboard()` (sdstudio), which can download data ([storing-data](https://surveydown.org/docs/storing-data), [features-roadmap](https://surveydown.org/docs/features-roadmap)). No codebook, no JSONL. Multi-selects are stored pipe-joined (`"red|blue"`) and matrix rows as `<id>_<row>` columns (NEWS 1.3.0), roughly like our `;` join and `r_1` columns.
- No RBAC (a single password on the dashboard), no groups, no immutable published versions, no QR/link management; edits to `survey.qmd` change the live survey.
- Staff side (sdstudio): GUI builder with drag-and-drop pages, live preview, Build/Preview/Responses tabs. Conditionals and reactive questions are **not yet** in the GUI (roadmap To Do). So its builder and its logic do not currently compose.

**Other things it has that we do not:** image-choice cards, sliders, date pickers, URL-parameter pass-through and external redirect (panel-vendor completion URLs), randomization, YAML question files, custom system-message languages, Bootstrap/SCSS theming, an "Agentic Skill" doc page for LLM authoring ([agentic-skill](https://surveydown.org/docs/agentic-skill), page exists, not read).

## 3. What to borrow (and from where)

1. **Pages as `---` plus an id; fenced-div form as an equivalent.** surveydown accepts `--- page1` (a new `---` closes the previous page) and `::: {.sd_page id=page1}`, "identical pages" ([page-navigation](https://surveydown.org/docs/page-navigation)). Our design already says pages are `---` or `##` headings. Borrow: give pages an optional **id** so conditions and skips can target them. Suggested: `--- id=consent` or an `## Heading {#consent}` pandoc attribute, which is native pandoc and fits grammar.md. Keep both forms compiling to the same `pages[]` model.
2. **Target-by-id for both questions and pages, one mechanism.** `sd_show_if(cond ~ "target_id")` works on questions and pages with the same id namespace. Borrow: allow `show-if` on a page marker as well as on a question div, and require page ids to share the uniqueness check with question ids (grammar.md already forbids duplicate ids). Origin: [conditional-logic](https://surveydown.org/docs/conditional-logic).
3. **Keep the condition next to the question, not in a separate server file.** This is where we deliberately do better; surveydown's separation (condition in `app.R`, question in `survey.qmd`) makes the survey a pair of files that must stay in sync, and conditions are arbitrary R. Keep `show-if="..."` inline. This is a confirmation, not a borrow.
4. **`is_answered(id)` as a primitive.** `sd_is_answered("q")` is the idiom for "show Q2 only once Q1 has a value" ([conditional-logic](https://surveydown.org/docs/conditional-logic), [reactivity](https://surveydown.org/docs/reactivity)). Add `answered(id)` to the safe expression grammar. Note our answer model already defines "unanswered" precisely (null/blank/empty array/empty object; grammar.md "Answers"); reuse that definition so browser and server agree.
5. **Distinguish show-if (visibility) from skip (navigation).** surveydown has `sd_show_if` (hide/show) vs `sd_skip_if` (jump to a later page, e.g. `~ "screenout"`). For event feedback, jump-to-page is rarely needed; `show-if` on a page covers it. Defer skip; if added, forward-only (surveydown added skip-back late, v0.15.0 per [features-roadmap](https://surveydown.org/docs/features-roadmap), and it complicates "submit once" and answer-dropping).
6. **Cross-page conditions and ordering rule.** surveydown tests cross-page `input$` conditions (NEWS 1.3.0, testing note). Borrow the constraint implicitly: a condition may reference only questions on the same or **earlier** pages. Enforce at compile time with a line-numbered error ("Line N: show-if refers to '#x' which comes later"), which fits our existing error style and prevents forward-reference cycles.
7. **Hidden-answer semantics.** surveydown's `required` is blocked per page and `sd_stop_if` takes priority over required checks (NEWS 1.3.0). Our design already goes further (server drops answers to hidden questions and enforces required-if-visible). Borrow the *priority ordering* in the validator: condition-hidden questions are never required and never validated, before any other check.
8. **Validation messages as a separate construct (maybe, later).** `sd_stop_if(nchar(input$zip) != 5 ~ "Zip code must be 5 digits")` pairs a condition with a message. We already have `min`/`max`/`maxlength`; a generic `error-if="..." message="..."` would reuse the phase 3 evaluator. Not needed for phase 3; note it as optional.
9. **Option labels vs stored values.** `c("Label" = "value")` ([defining-questions](https://surveydown.org/docs/defining-questions)). Conditions on option text (`lang == 'Other'`) are fragile when wording is edited, and our rule is that option text is the stored answer. Possible grammar extension: `- Researcher {value=researcher}`. Probably out of scope given ADR 0015 (export column stability); mention only so it is a decision, not an accident.
10. **Chat-assisted authoring (phase 2).** They publish an "Agentic Skill" page for LLM-assisted survey authoring ([agentic-skill](https://surveydown.org/docs/agentic-skill); content not read). Worth reading before writing #13's grammar spec/examples, to see how they package syntax for an LLM.

Do **not** borrow: R-code question definitions, YAML-header required lists, per-session cookie restore, default capture of IP/user agent/screen size, free-form R conditions, live-websocket-per-respondent architecture.

## 4. Adopt or integrate instead?

No. Direct reasons, each against our stated requirements:

- **Privacy default is opposite.** Cookies on by default and IP + user agent + screen resolution captured by default (`R/server.R`). You can turn both off via YAML, but then the project's privacy posture is "configured correctly" rather than "structurally absent", and the privacy doc is silent on anonymity. We promise no cookies and no IP logging.
- **No RBAC, versions, or export story.** A single dashboard password; mutable survey file; no codebooks or JSONL. We would have to rebuild all of the staff side around it, i.e. most of what we already built.
- **Stack mismatch.** R + Quarto + Shiny + Postgres vs. our TypeScript everywhere (ADR 0007). Running it means a second runtime and a long-lived Shiny process per concurrent respondent group; fine at survey scale, but off our deploy path (Docker compose, Postgres).
- **Authoring is R code.** Our whole point (ADR 0003, 0008) is that non-programmers write markdown. surveydown's own answer for non-coders is a GUI that does not yet support conditionals.
- **Integration surface is poor.** There is no documented API or export format to consume; the only seam is the Postgres table.
- **Strengths are not our needs.** Rich question types, reactivity and theming matter for research experiments (conjoint, randomized designs, piped text), not for 15-question event feedback.

It is a reasonable tool for an R-fluent researcher who wants a quick, programmable, single-owner survey. For us it is a reference for grammar ideas (section 3) and a competitor to note in platform-survey.md (not listed there currently), not a base.

Caveats: I did not run surveydown, did not read the `randomization`, `performance`, `external-redirect` or `agentic-skill` pages, and did not verify cookie behavior empirically (the `use-cookies` default is from docs; the metadata capture is from source).
