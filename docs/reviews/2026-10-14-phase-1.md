# Phase-1 review, 2026-10-14

This review covers the phase-1 code at commit `23a3f4d` on `main`. Six reviewers looked at it independently. Each finding below is filed as a GitHub issue with the label `review`, and the issue holds the full evidence and acceptance criteria. This document is the consolidated summary. It also records the sign-off for the auth and permission review that [#33](https://github.com/seandavi/plainfeedback/issues/33) requires.

The reviewers' raw reports, screenshots and scripts were working material and are **not** committed. Where a finding cites a screenshot or script, the issue describes how to reproduce it instead.

## Method

Each reviewer was a separately prompted agent that had not written the code. They each worked in a clean worktree, against Postgres 17 in Docker, and reported on their own. None of them modified the repo.

| Reviewer | Focus | How they tested |
|---|---|---|
| Security and privacy (#33) | Auth, authz, sessions, tokens, CSRF, participant endpoints, logging, threat-model claims | Read all of `apps/server/src/*.ts`, the migrations, `packages/core/src/answers.ts` and the web markdown and fetch code. Ran `pnpm test` (436/436 passed) and `pnpm audit`. Attacked a running server with curl, using users, groups and sessions seeded in the database. |
| Data model | Schema, migrations, constraints, cursor, export shape, fitness for phases 2 and 3 | Applied every migration with seed data before 0005, 0006 and 0007 so the data migrations ran over real rows. Probed constraints, the trigger, cascades, `seq` and query plans at about 300k rows. Ran CSV-merge behaviour on a verbatim, type-stripped copy of `columnsFor`/`flatten`, not the running app. |
| UI/UX and accessibility | Participant page and every staff screen | Built the app and drove it with Playwright in headless Chromium at 1440x900 and 390x844, in light and dark mode, keyboard only. Injected axe-core 4.10 (WCAG 2.0, 2.1 and 2.2 A/AA plus best practice) on six pages. Checked screen-reader semantics through Playwright's accessibility-tree snapshot. |
| Persona: responder | CFDE attendee on a phone and conference Wi-Fi | Playwright at 390x844, 320x568, 200% zoom and 200% text. Simulated network aborts, stalls and a server restart. Simulated 40 people behind one NAT with `X-Forwarded-For`. |
| Persona: creator | DCC coordinator who knows Google Forms | Two seeded creators editing the same draft. Made deliberate mistakes in the markdown. Published, closed, made a QR code, and built pre and follow-up waves. Desktop and mobile. |
| Persona: consumer | CFDE metrics engineer and qualitative researcher | Used viewer bearer tokens to submit 75 responses through the public API across three waves and two versions. Pulled JSONL and CSV, analysed them in polars, and tested the `since` cursor. |

**Not tested by anyone:**
- A real screen reader (NVDA, JAWS, VoiceOver). Accessibility-tree snapshots are only a proxy.
- A live OIDC login. Every reviewer seeded sessions. OIDC was judged by reading `auth.ts` and from the existing `auth.test.ts`, which runs real `openid-client` against a fake IdP.
- Browsers other than headless Chromium, including Safari and iOS.
- A real NAT. Shared addresses were simulated with `X-Forwarded-For`.
- Traefik on onclappc02, and whether its access log is really off for participant paths.
- Load, memory use and soak.
- Backup and restore.
- Parquet export, which is deferred and not implemented (`responses.ts` header).

Every finding records how it was established. **verified** means a reviewer reproduced it on a running system or database. **reading** means it comes from code reading only.

## Executive summary

- **Auth and permissions hold up.** No critical or high finding in authentication or authorization:
  - Every staff route is guarded.
  - Group isolation held against direct IDOR attempts.
  - CSRF held against every bypass tried.
  - Token scoping, role capping and disable/revoke behave as documented.
  - The threat model is accurate where it is current.

  The verdict on #33 is **fit for real data, with conditions**: two medium bugs must be fixed first ([#57](https://github.com/seandavi/plainfeedback/issues/57), [#58](https://github.com/seandavi/plainfeedback/issues/58)), plus the [deployment checklist](#deployment-checklist).
- **Privacy design holds up.** The participant page sets no cookies and no storage, makes same-origin requests only, uses a strict CSP and leaves no IP in logs or the database. Stored responses carry only a version, the answers, an hour-truncated time and `seq`.
- **The product loop is not yet self-serve:**
  - Staff cannot download responses from the web app ([#50](https://github.com/seandavi/plainfeedback/issues/50)).
  - The insert menu breaks a new survey on first use ([#51](https://github.com/seandavi/plainfeedback/issues/51)).
  - The default per-address rate limit would turn away most of a conference crowd on one Wi-Fi network ([#55](https://github.com/seandavi/plainfeedback/issues/55)).
- **The data is stored correctly, but exports are easy to misread.** The default all-versions CSV merges columns by name, so a reordered Likert statement silently changes what a column means ([#52](https://github.com/seandavi/plainfeedback/issues/52)). Rows do not say which survey, event or wave they come from ([#53](https://github.com/seandavi/plainfeedback/issues/53), [#54](https://github.com/seandavi/plainfeedback/issues/54)). Both matter for CFDE cross-event reporting.
- **Before the first real CFDE event**, the recommendation is to fix [#57](https://github.com/seandavi/plainfeedback/issues/57) and [#58](https://github.com/seandavi/plainfeedback/issues/58) for #33. Also fix the high items [#50](https://github.com/seandavi/plainfeedback/issues/50), [#51](https://github.com/seandavi/plainfeedback/issues/51), [#52](https://github.com/seandavi/plainfeedback/issues/52) and [#55](https://github.com/seandavi/plainfeedback/issues/55), together with [#60](https://github.com/seandavi/plainfeedback/issues/60). The remaining items can follow.

### Considered and not filed

- **Skip logic and multiple pages** (cre, missing feature): already tracked in [#14](https://github.com/seandavi/plainfeedback/issues/14), phase 3. The data-model review found the stored answer shape ready for it: `pages[]` exists and `visibleIf` is reserved.
- **Hour-truncated submission time prevents lag analysis** (con F5): a deliberate trade-off from #37 and ADR 0012. [#61](https://github.com/seandavi/plainfeedback/issues/61) (event date) gives an anchor at day granularity.
- **Global `seq` hints at other groups' volume** (sec F11, dm L6, con): accepted in ADR 0012.
- **Pre-0007 rows got `seq` in heap order** (dm L7): only matters if production had responses before 0007.
- **Migration 0005 `NOT NULL` without a default** (dm L3): no tokens existed before #11, so this had no real impact. The lesson for future migrations is in [#79](https://github.com/seandavi/plainfeedback/issues/79).
- **Small-cell suppression and retention automation**: already [#46](https://github.com/seandavi/plainfeedback/issues/46) and [#47](https://github.com/seandavi/plainfeedback/issues/47).
- **No audit log of staff actions, no HSTS from the app, unthrottled public GET**: documented in the threat model (#25, the TLS section, #4).
- **`__proto__` key dropped from answers**: harmless.
- **Branding, a custom thank-you text, a WYSIWYG editor, renaming events and published surveys, a test submission that is not counted** (cre, missing features, medium and low): nobody has asked for these yet. Revisit when a creator does.
- **Info items from the data-model review** (I1 to I3, I5): indexes are adequate at 300k rows; the DB lacks some CHECKs that the API enforces; `memberships.user_id` has no ON DELETE, which is consistent with "disable, don't delete"; the stored model has no schema version, so future changes must be additive.

## UI/UX and accessibility

**Key evidence.** axe found no violations on any page in light mode. Dark mode had one serious `scrollable-region-focusable` in the editor ([#78](https://github.com/seandavi/plainfeedback/issues/78)). The real problems are ones axe cannot catch:
- the insert control's position and keyboard behaviour ([#51](https://github.com/seandavi/plainfeedback/issues/51));
- the Likert required-error placement and association ([#56](https://github.com/seandavi/plainfeedback/issues/56));
- control border contrast at 1.6:1 and 1.9:1 ([#71](https://github.com/seandavi/plainfeedback/issues/71));
- focus and title management ([#68](https://github.com/seandavi/plainfeedback/issues/68));
- mobile layout of the privacy box and the closed notice ([#65](https://github.com/seandavi/plainfeedback/issues/65)).

Semantics were checked through the accessibility tree, not with a real screen reader. Treat [#66](https://github.com/seandavi/plainfeedback/issues/66), [#68](https://github.com/seandavi/plainfeedback/issues/68) and [#56](https://github.com/seandavi/plainfeedback/issues/56) as strong indications to confirm with NVDA or VoiceOver when fixing them.

**What works well:**
- Landmarks, headings, breadcrumbs with `aria-current`, and tables with captions and `scope`.
- Every choice question is a `fieldset`/`legend`. Each Likert statement is its own radio group, so arrow keys work within a row and Tab moves between rows. "(required)" is shown in text.
- On a validation error: an `role="alert"` summary, focus moves to the first invalid control, and server 422 errors are shown the same way.
- Targets of 44 px or more, 3 px focus rings, no horizontal scroll at 390 px, dark mode throughout.
- Editor: plain-English compiler errors with clickable line numbers; the preview keeps the last good version; Ctrl/Cmd+S; Publish disabled while there are unsaved changes; a guard against leaving with unsaved work.
- Native `<dialog>` with focus returned to the opener; destructive confirmations say what will happen.

## Data model

**Key evidence.**
- Stored data is correct and minimal. The risk is in how exports present it across versions and waves: [#52](https://github.com/seandavi/plainfeedback/issues/52), [#53](https://github.com/seandavi/plainfeedback/issues/53), [#54](https://github.com/seandavi/plainfeedback/issues/54), [#61](https://github.com/seandavi/plainfeedback/issues/61).
- The `seq` cursor is not commit-ordered ([#59](https://github.com/seandavi/plainfeedback/issues/59)), reproduced with two psql sessions.
- For [#52](https://github.com/seandavi/plainfeedback/issues/52), the data-model review used a copy of the export code. The consumer reproduced it on the running app.

**What works well:**
- **Immutability trigger:** the immutability trigger with its cascade-only exception (verified).
- **Hour truncation:** the hour-truncation CHECK and default hold, including under a +05:30 session time zone (verified).
- **Constraints:** consistent FK cascades, and a uniqueness constraint behind every slug lookup.
- **Migrations:** the journal and snapshot chain are linear, and the tests run the real migrations.
- **Publish:** it locks the survey row, so version numbers are consecutive.
- **Validation:** a single strict `validateAnswers` shared by client and server.
- **Codebook:** one per version, and accurate.
- **Phase 3:** additive only. `pages[]` exists, `visibleIf` is reserved and answers are flat by id.

## Privacy and security

**Key evidence.**
- Two medium bugs: [#57](https://github.com/seandavi/plainfeedback/issues/57) (token revival, verified live) and [#58](https://github.com/seandavi/plainfeedback/issues/58) (stream errors bypass redaction, verified live).
- One medium accepted risk made explicit: [#60](https://github.com/seandavi/plainfeedback/issues/60), ticket replay.
- Low-severity hardening, grouped: [#76](https://github.com/seandavi/plainfeedback/issues/76).
- Free text reaches every viewer verbatim. In the consumer's synthetic data, 12 of 134 answers contained an email address. Mitigations: [#50](https://github.com/seandavi/plainfeedback/issues/50) (warning next to the download), [#75](https://github.com/seandavi/plainfeedback/issues/75) and [#46](https://github.com/seandavi/plainfeedback/issues/46).

**What works well** (security review; [run] = verified live, [read] = code and existing tests):
- [run + read] **Authorization:** one choke point, `authorize`/`resolveGroup`. Handlers use only ids from the authorized path. Non-members get 404. Tokens are pinned to one group, capped at min(token role, current role), never admin, and need a current membership.
- [run] **CSRF:** an exact `Origin` match. Missing, `null`, subdomain and trailing-slash Origins all get 403. No method override and no CORS.
- [run + read] **Sessions:** 256-bit ids, stored as SHA-256 only. HttpOnly, SameSite=Lax, Secure. Idle and absolute expiry. Deleted when a user is disabled. New id on login.
- [read + tests] **OIDC:** PKCE S256, state and nonce. `email_verified` is required. Exact domain match and Google `hd`. Users are keyed by (iss, sub).
- [run] **Participant endpoints:**
  - No `Set-Cookie`, even when a staff cookie is sent. `no-store`, `no-referrer` and a strict CSP.
  - A 64 KB body limit, enforced for both Content-Length and chunked bodies.
  - Tickets cannot be forged or moved to another survey.
  - Unknown keys get 422. A closed survey gets 410 and a stale version 409.
  - Rate-limit keys are HMACed with a rotating in-memory key and never stored.
- [run] **Logging:** the access log holds `{method, path, status}` only. `onError` logs only the error class and SQLSTATE (the exception is [#58](https://github.com/seandavi/plainfeedback/issues/58)).
- [read] **Markdown:** rendered as React elements only, with no `dangerouslySetInnerHTML` (a test enforces this) and an href allowlist.
- [run] **Deletion:** cascades are complete and stay within the group.

## Deployment checklist

Do this on the production host before real data. Each item is described in [deploy.md](../deploy.md) or [deploy-auth.md](../deploy-auth.md).

- [ ] `ALLOWED_EMAIL_DOMAINS` is set to the staff domain(s). Empty means any verified email at the issuer can sign in, and Google `hd` is checked only when this is set.
- [ ] `ADMIN_EMAILS` holds the first admin only, and is **emptied after that admin has logged in once**. While it is set, it promotes on every login (sec F8, [#76](https://github.com/seandavi/plainfeedback/issues/76)).
- [ ] `TRUST_PROXY` matches the proxy (`x-forwarded-for` behind Traefik, `cf-connecting-ip` only when the origin accepts Cloudflare alone), **and the proxy is the only way in**:
  - The app is not reachable on :3000 from the host network or from other containers on the Traefik network.
